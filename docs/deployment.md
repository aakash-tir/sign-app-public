# Deployment — how the app gets onto the internet

> The build pipeline, what makes this app a PWA, how offline works, and where
> it actually lives once shipped. Written assuming you know roughly what
> "static hosting" and "HTTPS" mean but haven't worked with Cloudflare
> before.

## 1. The shape of "deployment" for this app

There is no server to deploy. The app is a bag of static files (HTML, CSS,
JS, model files, reference clips, an app manifest, a service worker) sitting
on a CDN. The user's browser downloads them once, caches the important ones,
and the app runs.

That means "deploy" is two steps:

1. **Build:** `cd frontend && npm run build` — Vite produces an optimized
   bundle under `frontend/dist`.
2. **Publish:** `npx wrangler deploy` — Cloudflare's CLI uploads that
   `dist/` folder to Cloudflare's edge network. Done.

Cloudflare automates both on every push to `main`. The only setup is
"connect the repo to Cloudflare once" (covered in §4 below).

## 2. What `npm run build` actually does

Vite is the build tool. When you run `npm run build` in `frontend/`, it:

1. **Compiles TypeScript to JavaScript** and bundles all the imports into a
   handful of optimized JS chunks. Tree-shaking removes unused code; minifier
   shrinks names; code-splitting separates the rarely-loaded chunks
   (MediaPipe and ONNX Runtime) so the main bundle stays small (~416 KB).
2. **Hashes filenames** for cache busting (`index-a3f9d.js` etc.) so users
   pick up new versions automatically.
3. **Runs the PWA plugin** (`vite-plugin-pwa`) — see §3.
4. **Drops the unused 26 MB of WASM** that `onnxruntime-web` ships by default
   (we load from a CDN at runtime instead — a custom Vite plugin handles
   this). Cloudflare has a 25 MB/file limit; this kept us under it.
5. **Copies `public/`** verbatim into `dist/` (the bundled MLP weights, the
   dynamic ONNX file, the reference clips, icons, etc.).

The result is `frontend/dist/` — about 5–10 MB of static files. That's the
artifact that gets deployed.

## 3. The PWA part

PWA stands for **Progressive Web App** — a regular website with three things
bolted on that make it feel like an installed app:

| | What it is | What we have |
| --- | --- | --- |
| **Web app manifest** | A small JSON file naming the app, its icons, its colors, its display mode. The browser uses it for "Add to Home Screen". | Generated by `vite-plugin-pwa` from config. |
| **Service worker** | A piece of JavaScript the browser runs *outside* the page, on a background thread. It intercepts network requests and can return cached responses, which is how offline works. | Generated by `vite-plugin-pwa` using Workbox. |
| **HTTPS** | Required for `getUserMedia` (camera) and service worker registration. | Cloudflare gives us free HTTPS. |

### Offline caching strategy

The service worker uses two caching policies (configured in
`vite.config.ts`):

- **Precache** (downloaded the moment the service worker installs): the app
  shell (HTML/CSS/JS), the bundled ONNX model, the reference clips. These
  are small and known up-front, so we cache them aggressively.
- **Runtime cache** (cached the first time they're fetched, served from
  cache thereafter): the MediaPipe WASM and `.task` model files, which load
  from Google's CDN at runtime. We use a **CacheFirst** strategy — once seen,
  always served from cache. That's how the app still works after you turn
  off your Wi-Fi.

The combination means: on first load, the user downloads ~10 MB total
(including MediaPipe). After that, the app is fully offline-capable
forever, until the service worker activates a new version on next deploy.

### Installation

On Android/Chrome/Edge, the browser pops a "Add to Home Screen" prompt after
a few visits. On iOS Safari, it's a manual menu item ("Add to Home Screen"
in the share sheet). Either way, the result is an app icon that opens the
PWA full-screen, looking and feeling like a native app — same camera, same
offline behavior, same IndexedDB.

## 4. Where it actually lives: Cloudflare Workers Static Assets

### What is Cloudflare?

Cloudflare runs a global network of servers ("the edge") in hundreds of
cities. They're best known for CDN (content delivery — keeping copies of
static content close to users) and security (sitting in front of sites). They
also offer hosting — which is what we use.

### What "Workers Static Assets" means in 60 seconds

Cloudflare used to have a product called **Pages** for static hosting and a
separate product called **Workers** for serverless functions. Recently they
merged the two: **Workers Static Assets** is Workers configured to serve
static files. The user experience is identical to old Pages, but the
underlying product is Workers.

For us this means:

- Push to `main` on GitHub → Cloudflare builds the project → Cloudflare
  publishes `frontend/dist/` to the edge → users get the new version within
  ~1–2 minutes. Free, fully automated.
- Every pull request gets a **preview URL** — its own temporary
  `*.workers.dev` deployment. You can test a milestone on a real phone
  before merging.
- HTTPS, custom domains, basic analytics — all included free.
- No backend, no database, no functions — just static files. Consistent with
  the on-device design.

### Config that makes it work

The whole deployment config lives in **`frontend/wrangler.jsonc`** — one
file. The interesting bits:

```jsonc
{
  "name": "sign-app",
  "main": "...",                     // (no Worker code; static-assets only)
  "assets": {
    "directory": "./dist",
    "not_found_handling": "single-page-application"
  }
}
```

The `not_found_handling: "single-page-application"` line is what makes
client-side routes (`/practice`, `/signs`, `/learn`, …) work on refresh.
Without it, navigating directly to `https://sign-app.../practice` would
return a 404; with it, Cloudflare returns `index.html` for unknown paths and
React Router handles the rest.

> Historical note: an early deploy used a Cloudflare Pages `_redirects` file
> with `/* /index.html 200`, which works on classic Pages but causes an
> **infinite loop** on Workers. The `wrangler.jsonc` setting above is the
> Workers-native fix.

### Build configuration (in the Cloudflare dashboard)

When the repo was first connected to Cloudflare, these are the settings
that were entered (and they don't change):

| Field | Value |
| --- | --- |
| Production branch | `main` |
| Build command | `npm install && npm run build` |
| Deploy command | `npx wrangler deploy` |
| Path | `frontend` |
| Environment variable | `NODE_VERSION=20` (Vite 8 needs Node 20+; Cloudflare's default was older) |

Every push to `main` automatically runs build → deploy. The Cloudflare
dashboard shows the live URL and the deploy history.

### The live URL

The deployed app is at **`https://sign-app.aakashtirathdas.workers.dev`**.
Custom domain attachment is available under "Custom domains" in the
Cloudflare project if/when desired.

## 5. CI: what gets checked before merge

Cloudflare auto-deploys whatever is on `main`. So the things that prevent a
broken deploy are the quality gates in **GitHub Actions**, configured in
`.github/workflows/`. Two independent CI lanes run on every PR:

### Frontend lane

```
prettier --check .       # formatting
eslint . --max-warnings 0  # linting (no warnings allowed)
tsc --noEmit             # type checking
vitest run               # unit tests (~150)
playwright test          # browser-driven e2e tests (~15)
```

If any one fails, the PR can't merge.

### ML lane

```
ruff format --check .    # formatting
ruff check .             # linting
mypy .                   # type checking
pytest                   # unit tests (~75)
```

This includes the **golden-vector tests** that lock the Python normalization
in step with the TypeScript runtime. A drift between the two would land here
as a red CI lane and block merge.

The rule is hard: **`main` is always green, and `main` is always shippable.**
A milestone branch only merges via squash-merge when both lanes are green.

## 6. The full path: from commit to deployed PWA

```
Developer pushes to a branch
         │
         ▼
Opens PR → GitHub Actions runs both lanes (frontend + ml)
         │                                       │
         │  green                                │ red
         ▼                                       ▼
Cloudflare builds a preview deployment    PR blocked; fix and retry
(unique URL for that PR)
         │
         ▼ approve + merge to main
GitHub fires push event → Cloudflare rebuilds main
         │
         ▼
`npm install && npm run build` runs on Cloudflare
         │
         ▼
`npx wrangler deploy` uploads dist/ to the edge
         │
         ▼
sign-app.aakashtirathdas.workers.dev serves the new version
(takes ~5 minutes for service workers to pick up the new
build for already-visited users; they get the old shell first,
then update on the next visit — standard SW behavior)
```

## 7. What we deliberately don't use

Cloudflare also offers serverless functions (Workers compute), databases
(D1, KV), object storage (R2), and more. We use **none** of them, because
the app is on-device-first by design:

- **No serverless functions** — recognition runs in the browser, not in a
  Worker.
- **No database** — progress is stored in the browser's IndexedDB.
- **No auth** — there is no account.
- **No object storage** — model files are bundled, not fetched at runtime.

If we ever add cloud sync (so progress follows you across devices), Workers
+ D1 + a tiny auth flow would be the natural fit. That's an explicit future
enhancement, not in scope today (ADR-005).

## 8. Local development

For everyday work you don't touch any of the above. Just:

```bash
cd frontend
npm install
npm run dev          # http://localhost:5173 (or similar)
```

Vite's dev server has fast hot-module-reload — edit a `.tsx` file, see the
change in <1 second. The PWA service worker is disabled in dev (so caching
doesn't surprise you while iterating); it activates on a production build.

To see a full PWA build locally with the service worker active:

```bash
npm run build
npm run preview     # serves dist/ on a local port
```

To run the test suites:

```bash
npm run test         # vitest (unit)
npm run test:e2e     # playwright (browser-driven, fake camera)
npm run typecheck    # tsc --noEmit
npm run lint         # eslint
npm run format       # prettier --check
```

And on the ML side:

```bash
cd ml
uv sync
uv run pytest
uv run ruff check .
uv run mypy .
```
